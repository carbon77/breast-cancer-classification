# Цели, ограничения, метрики и критерии успеха

**Связанный тикет:** `UNI-32`
**Статус:** проектное решение. Пороги зафиксированы до экспериментов. Значения с пометкой *предварительное* пересматриваются один раз после получения baseline-результатов (см. [раздел 6.1](#61-критерии-качества-финальной-модели-на-test)).

Документ дополняет [ML Design Doc](ml-design-doc.md). План экспериментов и единый split описаны в [baseline-experiment-plan.md](baseline-experiment-plan.md).

## 1. Цели и анти-цели

### Цели

- **G1.** Получить работающий end-to-end прототип: загрузка PNG-изображения → классификация (`normal`, `benign`, `malignant`) → результат с оценками по классам и версией модели.
- **G2.** Корректно сравнить три подхода в одинаковых условиях: базовая CNN, предобученная CNN (transfer learning) и ViT (transfer learning).
- **G3.** Выбрать финальную модель по заранее заданным метрикам и правилу выбора, а не по визуальному впечатлению.
- **G4.** Обеспечить воспроизводимость: seed, состав выборок, конфигурация preprocessing и версии зависимостей сохраняются вместе с checkpoint.
- **G5.** Показать оценки по всем классам и объяснение предсказания (тепловая карта) с явным указанием ограничений.
- **G6.** Обеспечить запуск приложения на ноутбуке без GPU.

### Анти-цели

- **AG1.** Не создавать медицинское изделие и не ставить диагноз. Результат нельзя использовать для клинических решений.
- **AG2.** Не заявлять клинически откалиброванные вероятности. Оценки модели показываются как выход классификатора.
- **AG3.** Не добиваться максимального качества любой ценой: тяжёлый подбор гиперпараметров на test-выборке не проводится.
- **AG4.** Не гарантировать качество на изображениях других клиник и аппаратов (domain shift).
- **AG5.** Не строить сегментацию опухоли. Тепловая карта не является медицинской разметкой.
- **AG6.** Не строить production-систему: аутентификация, хранение пациентских данных и масштабирование вне рамок проекта.
- **AG7.** Не сохранять загруженные изображения постоянно.

## 2. Ограничения

| Ограничение | Содержание | Влияние на решения |
| --- | --- | --- |
| Небольшой датасет | Breast Ultrasound Images Dataset: сотни изображений, три класса, выраженный дисбаланс | Transfer learning, аугментации только на train, регуляризация, early stopping; метрики по каждому классу |
| Вычислительные ресурсы | Обучение только на Colab Free: ограниченное время сессии, квоты GPU, возможные отключения | Небольшие модели и разрешение входа, сохранение checkpoint после каждой эпохи, лимит времени эксперимента |
| Среда запуска приложения | Ноутбук, без обязательного GPU | Инференс на CPU, лёгкая модель, загрузка модели один раз при старте backend |
| Медицинский контекст | Учебный исследовательский прототип | Предупреждение в UI, запрет клинических формулировок |
| Формат входа | Только PNG в первой версии | Валидация типа, размера и декодирования файла |
| Идентификаторы пациенток | Возможно, нельзя восстановить | Если split на уровне пациенток невозможен, фиксируется риск leakage |
| Размер checkpoint | Явного лимита нет | Размер измеряется и сообщается, но не является критерием приёмки |

## 3. Риски

| Риск | Вероятность / влияние | Признак | Митигация |
| --- | --- | --- | --- |
| Overfitting | Высокая / высокое | Train metrics заметно выше validation | Transfer learning, аугментации, weight decay, early stopping по validation macro-F1, сравнение train/val кривых |
| Class imbalance | Высокая / высокое | Низкий Recall у малого класса при высоком Accuracy | Анализ распределения, class weights или sampler (по train), стратифицированный split, macro-F1 как главная метрика |
| Data leakage | Средняя / высокое | Подозрительно высокое качество на test | Split до аугментаций; по возможности split на уровне пациенток; проверка дубликатов; фиксация ограничения, если ID недоступны |
| Latency | Средняя / среднее | Время инференса на CPU выше лимита | Измерение на ноутбуке, выбор более лёгкой модели, отключение градиентов, загрузка модели при старте |
| Стоимость и доступность GPU | Высокая / среднее | Отключение сессии Colab, исчерпание квоты | Checkpoint каждую эпоху, ограниченное число экспериментов, возобновление обучения, запасной вариант в Kaggle Notebook |
| Domain shift | Высокая / среднее | Падение качества на новых изображениях | Явное указание ограничения; оценка только на открытом датасете, без заявлений об обобщаемости |
| Ошибочная интерпретация | Средняя / высокое | Пользователь воспринимает оценки или heatmap как диагноз | Предупреждения в UI; оценки называются «выходными значениями модели» |
| Нестабильность результатов из-за малого test | Средняя / среднее | Большой разброс между seed | Несколько seed, отчёт mean ± std, анализ confusion matrix |

## 4. Иерархия метрик

Метрики выстроены сверху вниз: нижний уровень обеспечивает верхний.

```text
Business (условные, итоговое приложение)
    |
Product (поведение для пользователя)
    |
System (работа backend/frontend)
    |
ML (качество модели)
```

### 4.1. Business-метрики (условные)

Продукт учебный, поэтому «бизнес»-ценность формулируется как условные показатели итогового приложения.

| ID | Метрика | Определение | Целевое значение |
| --- | --- | --- | --- |
| B1 | Работающий end-to-end сценарий | Пользователь проходит путь «загрузка → результат» без ошибок на тестовых сценариях | 100 % контрольных сценариев пройдено |
| B2 | Полнота сравнения | Число архитектур, оценённых по единому протоколу | 3 из 3 |
| B3 | Воспроизводимость | Результаты финальной модели повторяются по сохранённым конфигурациям | Метрики совпадают в пределах допуска ±1 п.п. |
| B4 | Прозрачность ограничений | Предупреждение об исследовательском назначении и описание ограничений видны в UI | Присутствует на каждом экране результата |
| B5 | Простота демонстрации | Запуск приложения на ноутбуке по инструкции | Запуск без GPU и без ручных правок кода |

### 4.2. Product-метрики

| ID | Метрика | Определение | Целевое значение |
| --- | --- | --- | --- |
| P1 | Успешная обработка валидного PNG | Доля валидных PNG, для которых получен результат | 100 % |
| P2 | Корректная обработка невалидных файлов | Доля пустых, повреждённых и неподдерживаемых файлов, для которых UI показывает понятную ошибку без падения | 100 % |
| P3 | Полнота результата | Результат содержит класс, оценки по 3 классам, версию модели и предупреждение | 100 % ответов |
| P4 | Heatmap | Тепловая карта строится и отображается поверх изображения, наложение можно включить и выключить | Работает для финальной модели на всех тестовых изображениях; при сбое классификация остаётся доступной |

Качество объяснений (локализация) в критерии не включается: проверяется только то, что карта строится и отображается.

### 4.3. System-метрики

| ID | Метрика | Определение | Целевое значение |
| --- | --- | --- | --- |
| S1 | Время инференса | Среднее и p95 времени `preprocessing + predict` на одно изображение, CPU ноутбука | Среднее ≤ 1 с, p95 ≤ 2 с (*предварительное*) |
| S2 | Время ответа `POST /predict` | От получения запроса до ответа без heatmap | p95 ≤ 3 с (*предварительное*) |
| S3 | Время старта backend | Загрузка модели при старте | Модель загружается один раз; в запросах не загружается |
| S4 | Доступность `/health` | Ответ 200 при запущенном backend | 100 % |
| S5 | Устойчивость | Некорректный файл не приводит к падению backend | 0 падений на наборе негативных тестов |
| S6 | Безопасность ответов | Ответы об ошибках не содержат traceback и внутренних путей | 0 нарушений |
| S7 | Размер checkpoint | Фиксируется для каждой модели | Лимита нет, значение сообщается |

### 4.4. ML-метрики

Основная метрика выбора — **macro-F1**. Вспомогательные: Accuracy, Precision, Recall и F1 по классам, confusion matrix, multiclass ROC-AUC.

## 5. Определения ML-метрик

Пусть классы `c ∈ {normal, benign, malignant}`. Для каждого класса в схеме «один против остальных»: `TP_c` — верно предсказанные объекты класса c, `FP_c` — объекты других классов, предсказанные как c, `FN_c` — объекты класса c, предсказанные как другой класс. `N` — число объектов в выборке.

**Accuracy** — общая доля правильных предсказаний:

```text
Accuracy = (TP_normal + TP_benign + TP_malignant) / N
```

**Precision по классу** — доля верных среди предсказанных как класс c:

```text
Precision_c = TP_c / (TP_c + FP_c)
```

**Recall по классу** — доля найденных объектов класса c:

```text
Recall_c = TP_c / (TP_c + FN_c)
```

**F1 по классу** — гармоническое среднее Precision и Recall:

```text
F1_c = 2 * Precision_c * Recall_c / (Precision_c + Recall_c)
```

**macro-F1** — основная агрегированная метрика, все классы имеют одинаковый вес:

```text
macro-F1 = (F1_normal + F1_benign + F1_malignant) / 3
```

**Confusion matrix** — матрица 3×3, где элемент `M[i][j]` равен числу объектов истинного класса i, предсказанных как класс j. Используется для анализа типов ошибок. Особое внимание уделяется ошибке «`malignant` предсказан как `normal` или `benign`» (пропуск злокачественного случая).

**Multiclass ROC-AUC** (обязательная метрика) считается по схеме one-vs-rest с macro-усреднением:

```text
ROC-AUC_macro = (AUC_normal + AUC_benign + AUC_malignant) / 3
```

где `AUC_c` — площадь под ROC-кривой для задачи «класс c против остальных» по оценкам модели для класса c. Метрика не зависит от выбора порога и дополняет macro-F1.

**Дополнительно (system-уровень):** время инференса на изображение (среднее и p95) и размер checkpoint.

Все метрики считаются на **одной и той же test-выборке** для всех моделей. Test используется только для итогового сравнения. Подбор гиперпараметров и early stopping выполняются на validation.

## 6. Критерии успеха, зафиксированные до экспериментов

### 6.1. Критерии качества финальной модели (на test)

| # | Критерий | Порог |
| --- | --- | --- |
| M1 | Accuracy | ≥ 0,80 |
| M2 | macro-F1 | ≥ 0,75 (*предварительное*) |
| M3 | Recall по `malignant` | ≥ 0,80 (*предварительное*) |
| M4 | Macro ROC-AUC (OvR) | ≥ 0,90 (*предварительное*) |
| M5 | F1 по каждому классу | ≥ 0,60 (*предварительное*), чтобы ни один класс не «проваливался» |

Напрямую задан только порог **Accuracy ≥ 80 %**. Остальные числа выведены из него и отмечены как предварительные. После получения baseline-результатов (базовая CNN) пороги M2–M5 можно пересмотреть **один раз**, до оценки остальных моделей. Пересмотр фиксируется записью с датой и обоснованием. После этого пороги не меняются.

### 6.2. Правило выбора финальной модели

1. Основной критерий: максимальный macro-F1 на test.
2. Если разница macro-F1 между лучшими моделями меньше 1 п.п., выбирается модель с большим Recall по `malignant`.
3. Если и он различается меньше чем на 1 п.п., выбирается модель с меньшим временем инференса на CPU.
4. Модель, не выполнившая M1–M3, не может быть выбрана как финальная без явной записи об отклонении.

### 6.3. Требования к сравнению моделей

- Сравниваются минимум три подхода: базовая CNN, предобученная CNN (ResNet / EfficientNet / DenseNet) и ViT с transfer learning.
- Все модели используют **один и тот же split** train/validation/test и одну и ту же test-выборку.
- Split выполняется до аугментаций; аугментации применяются только к train.
- Каждая модель обучается минимум на **3 seed**; в отчёте приводятся среднее и стандартное отклонение macro-F1 и Accuracy.
- Для всех моделей фиксируются: архитектура и гиперпараметры, seed, состав выборок, preprocessing и аугментации, настройки обучения, время обучения и инференса, версии зависимостей, идентификатор checkpoint.
- Для всех моделей строятся confusion matrix и таблица Precision/Recall/F1 по классам.
- Подбор гиперпараметров допускается только на validation; число запусков на test не превышает одного итогового для каждой модели и seed.
- Бюджет обучения ограничен условиями Colab Free: один эксперимент должен укладываться в одну сессию с сохранением checkpoint после каждой эпохи.

## 7. Вне рамок

Реализация обучения, измерение фактических метрик и проверка достижения порогов выполняются в отдельных задачах. Этот документ фиксирует только критерии.
